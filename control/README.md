# RS-SDK control API

This is an optional plain HTTP API for managing one bot on the hosted RS-SDK
demo server from a remote tool that can make HTTPS requests. It doesn't
require MCP, a domain, or a desktop app.

## Install on Debian 13

First follow the [hosted headless quickstart](../docs/agent-quickstart.md) to
install Bun and both sets of dependencies. Use a stable public IPv4 address
when possible. Allow inbound TCP 80 (certificate validation and the health
check) and 443 (HTTPS) in the hosting provider's firewall.

Run from the repo root as your regular sudo-capable Linux user:

```sh
bash control/install.sh YOUR_PUBLIC_IPV4
```

The installer starts a systemd service listening on loopback, configures Nginx,
and requests a short-lived Let's Encrypt certificate for the IP. A systemd
timer checks for renewal twice a day. It creates a random API token at
`~/.config/rs-sdk-control/token` with owner-only permissions and preserves it
on subsequent installs. It does not log in a bot, copy bot credentials, or
start a task. No API key should be included in a URL.

On the server, the installer checks the certificate and HTTPS health response.
Then from the intended remote caller, check `https://YOUR_PUBLIC_IPV4/health`
without a token. If your environment restricts egress, it must allow this
address for the API to work. Port 80 serves only health and ACME validation;
use HTTPS for every authenticated request. [Let's Encrypt IP certificates](https://letsencrypt.org/2026/03/11/shorter-certs-certbot)

For a remote caller with its own secret storage, optionally pass a second
argument to the installer. It must be the SHA-256 hex digest of the entire
`Bearer <token>` header value (without a trailing newline), where `<token>`
is a random 256-bit secret generated by the caller. Only the digest travels
to Lightsail. An installation without a second argument preserves any
previous caller digest. To revoke that caller, remove `caller.sha256` from
the config directory and restart the service.

### If your client can reach the IP but its proxy rejects IP certificates

After the installer succeeds, add an HTTPS hostname with:

```sh
bash control/add-ip-hostname.sh YOUR_PUBLIC_IPV4
```

This uses the public [sslip.io](https://sslip.io/) DNS service to resolve the
IP-derived hostname directly to your instance. It adds a separate Nginx site
and a certificate for that hostname. Your IP endpoint, API token, and service
stay in place. The command prints the new HTTPS health URL after validating
the certificate. If the public IP changes, install again for the new address.

## Optional GitHub push sync

After the HTTPS hostname is working, install the receiver on Lightsail as
your regular sudo-capable user:

```sh
bash control/install-github-sync.sh
```

In `notdiogenes/rs-sdk`, open **Settings → Webhooks → Add webhook**. Use the
payload URL printed by the installer, select `application/json`, and paste the
contents of `~/.config/rs-sdk-github-sync/secret` into **Secret**. Enable SSL
verification and select **Just the push event**. GitHub sends a `ping` after
registration. Check **Recent Deliveries** for a `204` response.

A signed push to `main` queues a fast-forward of `~/rs-sdk-sync` and returns
`202`. The harness decides when to use source from that checkout. The sync
service leaves the bot checkout and running services alone. It runs Git only
after a push, or to finish a pending sync at service startup. Keep the sync
checkout clean. After a push, check `git -C ~/rs-sdk-sync rev-parse HEAD` and
`journalctl -u rs-sdk-github-sync -n 30` for the synced revision.

## Optional public bot status page

With the HTTPS hostname and GitHub sync installed, run on Lightsail:

```sh
bash ~/rs-sdk-sync/control/install-public-status.sh
```

The installer prints the public `/bots` URL. The page lists bots with a
`bot.env` in the controller's `bots/` directory and shows their game status,
activity, and current location. The Location column shows world X and Z and
the map plane when available. It shows a dash for offline bots, stale data,
or missing coordinates. Activity comes from a running task managed by the
control API or from combat reported by the game client. If neither is
available, the page says so. Stale or failed game checks appear as **Unknown**.
**Last activity** shows the latest action and timestamp reported by a running
mining or shark-fishing script. When no script action is available, it shows
the last observed position or floor change, XP gain, or combat change. The service checks
every 15 seconds from the latest local client frame, with a gateway read
for clients that do not publish to Fleet Desk. Inventory and Diagnostics
use the same state source. The service keeps the observation
time across dashboard restarts and logouts and displays it in US Eastern time.
A dash means no activity has been observed since tracking started.
The page refreshes every 15 seconds while open. It serves only the public
fields and runs in a separate service from the control API and gameplay
processes.

The Fleet desk groups bots by recent game activity and connection or task
issues. **Running** means combat is in progress or movement, XP gain, or
a combat change was observed in the last two minutes. A running managed task
without an observed effect for five minutes appears under **Needs attention**.

With a dashboard session, **Quests** shows one row per bot, total quest points
below each bot's name, and one column per Quest Journal entry. The dashboard
keeps each account's most recent observed journal,
including while the account is offline. **Unreported** means no journal state
was observed for that quest. Per-quest markers require a bot client running
code that publishes Quest Journal telemetry.

**Stats** shows last observed base levels and combat level. **Check banks**
reads locally saved balances and item stacks when opened. Managed clients
capture bank contents as the game sends updates, including short bank visits.
Older clients can save a bank when a fleet sample sees it open.
Checking the dashboard never opens a bank in-game. XP on a
Fleet card is the gain between samples taken within the last hour. Timestamps
on the dashboard use US Eastern time.

Fleet Desk uses two systemd services from `~/rs-sdk-sync`. The web service
serves the page and report responses. The worker supervisor owns bot clients,
active tasks, saved plans, and audit recording. The services communicate over
a private Unix socket. Restarting the web service keeps the supervisor and
its active tasks running. The webhook has separate restart rules for web and
worker source changes.

Run the installer above once between runs to move an existing installation
to the separate services. The migration stops the old combined service before
the new supervisor opens its databases. Saved running plans resume on the
new supervisor. Until this migration, the old automatic restart watcher
leaves the combined service running.

Open the one-time setup link to choose a password of at least 12 characters.
After setup, use **Sign in** with your dashboard password. You can also set or
reset the password from your Lightsail terminal:

```sh
bash ~/rs-sdk-sync/control/set-dashboard-password.sh
```

Sign in once per browser. The server session has no expiration date, and
the browser cookie is renewed when you use the dashboard. Signing out
revokes that session. Changing the password revokes every dashboard session.
Programmatic callers can continue to use the bearer token.

The managed bot row has a **Start activity** or **Stop activity** button.
Choose a task and select **Start activity**. The dashboard service starts the
managed game client if needed, waits for live game state, and launches the
task. You can close the dialog while it is starting. **Stop activity**
cancels a pending start or ends the task and keeps the client logged in.

Select **Diagnostics** on a bot's card after signing in to see that bot's
managed client and task,
the latest task exit code, startup errors, game-state freshness, and the
last movement and XP gain observed. For scripts that report an HP recovery
pause, the panel shows the current HP and the level needed to resume. The dashboard samples every 15 seconds
and saves recent lifecycle events across dashboard restarts. The panel uses
the existing session and is read-only.

## Optional bot configuration

Before enabling gameplay, put the bot's existing `bot.env` and scripts in
`bots/<name>/` on the server as described in the quickstart. Keep credentials
out of Git. Use the hosted demo server in `bot.env` and keep
`GATEWAY_URL` unset. Create `~/.config/rs-sdk-control/control.json`:

```json
{
  "bot": "Example",
  "tasks": {
    "train": "train.ts"
  }
}
```

A task is a local filename in that bot directory using the normal standalone
`runScript` entry point. The API accepts an allowlisted name only. It doesn't
accept code, shell commands, or file paths from callers. Changes to this
allowlist take effect the next time the API starts the lite client.

## Requests

Send `Authorization: Bearer <token>` for every request other than
`GET /health`. Store the token in the calling application's secret store or
read it interactively into an environment variable for a shell client. Do
not paste the token into chat or put it into source code.

| Method and path | Result |
| --- | --- |
| `GET /health` | Process health only, no game data |
| `GET /v1/status` | API-managed client/task and the last task exit result |
| `GET /v1/state` | Gateway snapshot with tick, state age, combat, skills, inventory, and equipment |
| `POST /v1/client/start` | Start one lite client for the configured bot |
| `POST /v1/task/start` | Start an allowlisted task with JSON such as `{"task":"train"}` |
| `POST /v1/task/stop` | Stop the task |
| `POST /v1/client/stop` | Stop the task and lite client |

A start returns `202` for process creation. Poll state and status to verify
game login and task progress. The age field distinguishes fresh and cached
state. A task requires a managed client and a fresh snapshot. Use a single
controller; do not run the same bot through Codex/MCP while the API manages it.
On reboot or service restart the API comes back, but client/task processes
are deliberately not resumed. Inspect local logs with
`journalctl -u rs-sdk-control -n 50`.

### Test with one movement

To configure an existing hosted bot for a single-step interaction test, run
`bash control/prepare-smoke.sh "BOT_NAME"` as the user that installed the API.
It reuses the bot's credentials if present and asks for its existing password
in the terminal otherwise. It adds the `smoke-move` task without starting a
client or task. When the operator authorizes the test, start the client, read
a fresh location, run `smoke-move` once, and verify the new coordinates.

### Fleet desk activity and inventory controls

Choose **New bot** to create a hosted profile and start its first activity plan,
or **Plan activities** on a roster card. Leave the name blank to generate one.
The dashboard stores new profiles under its private runtime `bots/` directory
and starts their lite clients. A first-login setup step verifies arrival in
Lumbridge before the requested activities start.

Plans are ordered. Quests finish when the live journal confirms completion.
Repeatable activities can run for a duration, until a supported skill reaches
a target level, or indefinitely as the last step. Add quest or level
prerequisites to any step. The controller evaluates built-in and added
requirements before launching a step. For example, it uses Men, Guards, and
Knights to close a Thieving gap as those targets become available, and trains
Hitpoints separately if the Heroes plan requires it. The Heroes activity has
an 80 Hitpoints floor in the planner.

A paused plan retains its current step and credited time. Timed steps count
time while their activity and the game client are running, including travel
and recovery. Plans and credited time persist in `activity-plans.sqlite`.
After a service restart, an active plan reconnects and checks live state before
continuing. A blocked plan shows why it stopped and can be resumed. Open
**View plan** and choose **Edit plan** to change a saved plan while it runs.
Edits to upcoming activities preserve the current task and credited time.
A change to the current activity can also keep its task running when it needs
the same task and launch settings. Pausing leaves its managed client online.

Use `GET /bots/activity?view=plan` to fetch the catalog, or add `&bot=NAME` to
read a saved plan. A signed-in session or control Bearer credential can POST
`{ "action": "start", "steps": [...] }` with the bot query, or
`{ "action": "create", "name": "", "steps": [...] }` without it. To edit a saved
plan, POST `{ "action": "update", "expectedRevision": "...", "steps": [...] }`
with the bot query and the plan's current `revision` from GET. A stale revision
returns `409`. Existing plans also accept `pause` and `resume`. The catalog
specifies each activity’s
finish modes via `usage` and `trains`. Example step:

```json
{
  "task": "pickpocket-men",
  "finish": { "type": "minutes", "minutes": 30 },
  "requirements": [{ "type": "quest", "task": "cooks-assistant" }]
}
```

Single-task HTTPS controls still work. A roster bot running a client outside
Fleet desk must sign out of that client before Fleet desk can launch one.

The inventory dialog reads the selected bot's fresh backpack contents from
game state. It reports offline or stale state when a current snapshot is
unavailable. Use `GET /bots/activity?view=inventory&bot=NAME` with a dashboard
session, or use `/bots/activity?bot=NAME` for bot-specific task controls.
`GET /bots/activity?view=diagnostics&bot=NAME` accepts the dashboard session
or control Bearer credential and reads the selected bot's diagnostics. Fleet desk uses a separate client
and task process per bot. It can take over from an idle primary controller
client when starting a plan.

### VPS resource monitor

Open **Monitor** beside **New bot** to see CPU, resident memory, VPS PIDs,
and start times for Fleet Desk's managed Lite clients and SDK tasks. The
shared pathfinder appears once. The worker samples every 500 ms and keeps up
to one hour of readings in memory.

Use `GET /bots/activity?view=monitor&window=30` with a dashboard session or
control Bearer credential. The window is in seconds and accepts `30`, `300`,
or `3600`. Samples include timestamps for matching PIDs against `atop`.

### Fleet Desk updates

Fleet Desk loads its page, browser assets, and read-only audit reports from one
committed Git revision. A UI update takes effect on the next page load. If a
presentation fails to load, Fleet Desk keeps serving the previous version.
The worker loads compatible plan, activity catalog, and API changes in place
and keeps the last compatible version if a reload fails. Running tasks keep
the script and tracked dependencies from their launch revision. The next
task launch uses the updated compatible release. An operator edit that
changes launch arguments can still relaunch the affected task.

The Fleet Desk **Updates** panel compares managed runs with the latest
release and checks saved settings for unfinished steps. **Update all
compatible runs** schedules each eligible task at its next safe checkpoint.
Mining, fishing, pickpocketing, and combat training can report checkpoints.
The worker waits for the old task to exit before launching its replacement
on the connected client. **Update now** checks fresh game state, health,
combat, and open game windows before stopping a task on request.

An incompatible queued step waits for a settings review at launch. A
running step keeps its release until the user reviews its settings and the
task reaches a safe checkpoint. For behavior changes to saved options,
increase the activity's `settingsVersion`. Declare a `settingsMigrations`
entry only when it can preserve the previous behavior.

On an existing host, the first update to this worker leaves the old process
and its bots running. Activate the checkpoint-capable worker during a maintenance window by
restarting `rs-sdk-fleet-workers.service` once after the checkout syncs.
Fleet Desk restores saved running plans after that restart. Subsequent
changes to the process supervisor, game client, or shared pathfinder still
use a worker restart.

### Activity audit history

Fleet desk stores activity runs in `activity-audit.sqlite` in the dashboard
runtime directory. Each dashboard-managed task and the Lumbridge demo worker
record lifecycle events, selected SDK action dispatches, observation timeouts,
and periodic game snapshots. The audit starts collecting when it is deployed.
It does not import earlier dashboard events or cover standalone and primary
`/v1` scripts. Requests are read-only and accept a dashboard session or a
control Bearer credential.

In Fleet Desk, open **Audit history** from the toolbar to browse the fleet, or
from a bot's card to filter to that bot. Choose **Runs** for the timeline and
retained evidence, **Summary** for grouped totals, or **Insights** for phase
time, outcomes, throughput, setbacks, and daily trends. Chart labels and
ranked issues can open a representative trace. API requests use
`format=json` by default. Use `format=html` to open the matching Fleet Desk
view in a browser and prompt for dashboard sign-in when needed.

An agent with the dashboard password can POST to the same audit URL with
`Content-Type: application/json` and a JSON body containing `password`.
The response contains the requested report and sets the dashboard session
cookie. Reuse that cookie for subsequent GETs. Supply the password from a
secret variable in the POST body. Keep the password out of query strings.
GET also accepts an existing dashboard session or authorized Bearer credential.

| HTTPS request | Result |
| --- | --- |
| `GET /bots/activity?view=audit&mode=summary&days=35` | Cross-bot phase totals, milestones, setbacks and repeated breakpoints grouped by task and revision |
| `GET /bots/activity?view=audit&mode=insights&task=pickpocket-knights&days=35` | Chart data, sample sizes, run statuses, rates, daily trends, and representative run IDs |
| `GET /bots/activity?view=audit&mode=runs&bot=A%20Pirate&days=14` | Recent run IDs, script hashes, exit status and failure locations |
| `GET /bots/activity?view=audit&run=RUN_ID` | Phase totals, retained failure evidence and the latest chronological events for the run |

Use `task=TASK_ID` to narrow reports and `phase=PHASE_ID` to narrow summaries
and detail streams. Use `limit` (1–100, default 50) and the returned
`nextBefore` as the next request's `before` cursor. Summary and run-list
windows cover runs started within the requested 1–35 days. The store keeps
run summaries, bounded terminal failure evidence, and the latest evidence
sample for each setback type per run and phase for 35 days. Detailed
events share a rolling budget of 240,000 across bots, so older detail can age
out sooner.

Insights accepts the same bot, task, and phase filters and a `revision` filter
using a full commit SHA or a prefix of at least seven characters. Its totals
use runs started in the window. Pickpocket success rates use all recorded
pickpocket outcomes as the denominator. A single instrumented activity can
show XP or coins per hour using its recorded time across all phases,
including search and recovery.

Daily trend counters use hourly buckets independent of raw events and are
grouped in US Eastern time. The trend window begins on an hour boundary and
includes activity recorded in the window even for runs that started earlier.
The coverage timestamp marks the start of available trend counters. Historical
run totals appear immediately. Date-specific coverage begins when Insights is
deployed, with a partial current day.

For a repeat quest breakpoint, start with `breakpoints` and open a matching
run. A floor-change trace records the scanned candidates, the selected ID and
option, the starting location, the expected plane or region change, the SDK
result and the observed location and system feedback. A dispatched action
and a confirmed game effect have separate records. The run also reports the
terminal error and its source frame when the script supplies a stack.

For Witch's House, filter by `task=witchs-house&phase=garden-crossing`.
Compare garden attempts, successful crossings, catches, elapsed time, and
dispatch and timeout counts by strategy and revision. The report counts those
signals both in successful runs and before later failures. Detailed garden
legs include the bot position and, when visible, the witch's position at the
start and end of each leg. The current instrumentation labels the existing
strategy `direct-waypoints`.

#### Activity-specific diagnostics

| Activity | Evidence in the audit |
| --- | --- |
| Pickpocketing, including Ardougne Knights and the adaptive script | Requirement check, travel, search waypoints and NPC candidates, target and option, action outcome, selected game feedback, XP and coin gains, HP loss, stun waits, food, banking, and deaths |
| Cow and Hitpoints training | Target searches, engagement results, observed XP, equipment or recovery, and deaths. Cow training also records combat style, loot, bone burials, and bank space. |
| Tutorial exit | Starting tile, every skip attempt, and confirmation that the bot reached the Lumbridge surface |
| Bundled quests | Named quest phases, journal verification, dialogue choices, travel, and inventory/loadout checks, with activity-specific evidence such as the Witch's House crossing |

For Knights, use `GET /bots/activity?view=audit&mode=summary&task=pickpocket-knights&days=35`.
The matching `pickpocket-attempt-*` signals count successful attempts, stuns,
and other outcomes separately. Their `elapsed_ms`, `xp_gained`, `coins_gained`,
and `hp_lost` fields sum observed attempt costs and gains. Phase duration
includes separate time for search, stun waits and recovery, and updates as
events arrive even while the run is active. Setbacks retain sampled evidence.

Pickpocket run details also record decisions and pair each operation's
`intent` and `result` events. Read `data.intent` for the reason, the intent
event's parameters and starting state for the selected action, and the result
event's `outcome`, elapsed time, and end state for what happened. The matching
`data.operationId` ties both records to underlying SDK dispatches. A nested
wait includes its `parentOperationId` in the intent event. A pending intent may
still be in progress. Inspect the run state and adjacent events if its result
is absent. The trace includes target selection, travel, retries, waits, food,
banking, and recovery.

### Separate Lumbridge pickpocket demo

The HTTPS dashboard also exposes a second, isolated client and task for the
bundled demo tasks. This uses the existing owner or delegated control
Bearer credential. The primary `/v1` controller keeps its own bot and task.
Use the dashboard hostname with the following requests.

| Method and path | Result |
| --- | --- |
| `GET /bots/activity?demo=status` | Demo character, process IDs, start times and last exit codes |
| `POST /bots/activity?demo=client/start` | Create the demo character on first use and start its headless client |
| `GET /bots/activity?demo=state` | Snapshot freshness, tile/plane, HP, Thieving XP, coins, nearby Men and their action options, matching system messages and operation feedback |
| `POST /bots/activity?demo=task/start` | Start an allowlisted task with `{"task":"pickpocket-men"}` or `{"task":"train-hp-pickpocket"}` after the client reports live state |
| `GET /bots/activity?demo=events` | Latest 200 lifecycle and structured script events, including tutorial exit and pickpocket outcomes |
| `POST /bots/activity?demo=task/stop` | Stop the script and keep the demo character logged in |
| `POST /bots/activity?demo=client/stop` | Stop the script and log the demo character out |

The `pickpocket-men` task skips Tutorial Island if needed and stays in
Lumbridge. The `train-hp-pickpocket` task trains base Hitpoints to 60, then
travels to East Ardougne and picks an available target based on Thieving
level, with Heroes ahead of Knights. Guards are the training target from
40 to 54 Thieving. The
attached client and task run on the dashboard host. Once provisioned, the
demo appears in the Fleet desk roster, including while offline. A dashboard
service restart ends both processes and clears the event buffer. The demo's
credentials stay on the host in the dashboard's private runtime directory
so the same demo character can be started again. Each start returns `202`.
Use the state and events responses to verify login and in-game effects.
